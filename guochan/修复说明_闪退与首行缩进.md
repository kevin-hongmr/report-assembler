## 一、任务栏显示 Python 图标（已修复）

### 根因

UKUI 的任务栏解析器是 `/usr/bin/panel-daemon`（ukui-panel 3.25.0.0）。反查其二进制字符串：

* **里面根本没有 `StartupWMClass` 这个字符串** —— 也就是说，先前在
  `~/.local/share/applications/wenhui-assembler.desktop` 里写的 `StartupWMClass=`
  对 UKUI **完全不生效**（它读的是 GNOME/KDE 的规则，不是 UKUI 的）；
* 它实际用的键是 `/usr/share/applications/`、`/.local/share/applications/`、
  `/proc/%1/cmdline`、`NoDisplay`、`.desktop`，即按 **窗口 app-id / 进程 cmdline
  ↔ 桌面项文件名** 匹配。

而 Qt6 在 xcb 下把 `WM_CLASS` 写成 `"<argv[0] 的 basename>", "<applicationName>"`。
程序由 `python3 app/main.py` 启动，argv[0] 是 `main.py`，于是实测得到：

```
WM_CLASS(STRING) = "main.py", "wenhui-assembler"
                    ^^^^^^^^^  匹配不上 → 回退按进程名找 → python3
```

系统里恰好有 `/usr/share/applications/python3.8.desktop`
（`Exec=/usr/bin/python3.8`、`Icon=/usr/share/pixmaps/python3.8.xpm`），
于是任务栏取到了 **Python 图标**。这解释了为什么先前的改动"看起来对、却没用"。

### 修法（两处，缺一不可）

1. `app/main.py`：创建 QApplication **之前** 执行 `sys.argv[0] = APP_ID`。
   实测（本包自带 PyQt6 6.7.3 + Xvfb）：

   ```
   WM_CLASS(STRING)          = "wenhui-assembler", "wenhui-assembler"
   _GTK_APPLICATION_ID       = "wenhui-assembler"
   _KDE_NET_WM_DESKTOP_FILE  = "wenhui-assembler"
   ```

   三个来源全部指向 `wenhui-assembler.desktop`，桌面环境读哪一个都能命中。

2. `启动汇编程序.sh`：改用 `exec -a "$DESKTOP_ID" "$PY" app/main.py`，让
   `/proc/<pid>/cmdline` 的 argv[0] 也不再是 `python3`（覆盖面板按 cmdline 回退匹配的路径）。
   **注意不能写成 `exec -a X env ...`**：`env` 会重新 exec 并把 argv[0] 改回去，
   所以 PYTHONPATH 改用 `export` 传递。

### 顺带

启动后 1.5 秒会往日志写一行窗口身份自检，任务栏再不对时先看这行：

```
[INFO] app.ui.appicon: 窗口身份自检：WM_CLASS=... | _NET_WM_ICON=非空 | AppId=...
```

## 二、预览中首行缩进两个字符不生效（已修复）

### 根因（实测）

原实现只写 `w:firstLineChars="200"`，并**刻意删掉** `w:firstLine`（twips）。
用随包 LibreOffice 6.4 实测三种写法：

| docx 里的写法 | 渲染后首行缩进 |
| --- | --- |
| 只写 `w:firstLineChars="200"` | **0（无缩进）** |
| 只写 `w:firstLine="640"` | 32 磅 = 2 个 16 磅字符 ✓ |
| 两者都写 | 32 磅 ✓ |
| `firstLine` + `hanging="0"` | **0（hanging 压掉 firstLine）** |

结论：

* **LibreOffice 完全忽略 `firstLineChars`**。成品在 Windows/WPS 下正常，是因为 WPS 认
  字符缩进；而**预览与 PDF 走的是 LibreOffice**，于是只有预览丢了缩进 —— 与用户描述完全吻合。
* `w:hanging` 与 `w:firstLine` 映射到同一个内部属性，**hanging 优先**（哪怕写 0），
  所以原来"把 hanging 显式置 0"的做法会连带把 twips 缩进一起废掉。

### 修法

`app/core/assembler.py`：

* `_set_first_line_indent(p, chars, size_pt)` 同时写两个属性：`firstLineChars = chars*100`
  （WPS 权威值）与 `firstLine = chars × 字号 × 20`（LibreOffice 唯一认的等值 twips），
  两者数值等价，谁被采纳结果都一样；
* `w:firstLine`、`w:hanging`、`w:hangingChars` 一律**删除**而不是置 0；
* 各调用点传入该段落实际字号（`_apply_para_uniform` 新增 `size_pt` 参数），
  保证用户改了正文字号后缩进量仍等于两个字符。

### 验收（同一段落前后对比，随包 LibreOffice 渲染）

| | 该段首行 x0 | 正文左边界 | 首行缩进 |
| --- | --- | --- | --- |
| 修复前 | 76.70 | 76.70 | **0** |
| 修复后 | 108.70 | 76.70 | **32.00 磅 = 2 字符** ✓ |

## 三、运行途中闪退（已加固 + 加装崩溃取证）

### 已排除

* 内存不足（主机 16 GB + 20 GB swap，工作目录仅几十 MB）；
* 汇编 / 预览逻辑本身（真机与沙箱各跑通一次：9 份文档 → 汇编 → 145 页预览，退出码 0）；
* 单纯的文件对话框（12 次开关对话框压测无崩溃）。

### 关键证据

用户日志里崩溃点**连"未捕获异常"都没有**，而 `logger.py` 早已装了
`sys.excepthook`（任何 Python 异常都会入日志）。→ 判定为 **C 层硬崩溃**（SIGSEGV/SIGABRT）。
且日志断点严格落在对话框之前：

```
00:23:48 主窗口初始化完成
00:24:39 开始生成预览：7 份文档      ← 添加 7 份文档耗时 51 秒（主线程被完全阻塞）
00:24:45 预览生成完成：42 页
00:25:46 日志系统初始化完成…         ← 中间无「开始汇编」行 → 崩溃在 getSaveFileName 内部
```

### 本次修掉的确定性缺陷

1. **`add_files` 在 GUI 线程里做重活**：识别标题/单位会调用 LibreOffice 转换
   `.doc/.wps`，7 份文档实测阻塞主线程 **51 秒**，期间窗口完全冻结（桌面环境可能据此
   判定"无响应"）。→ 改为后台线程执行，实测 6 份文档 **3.0 秒**完成且界面不冻结。
2. **后台线程生命周期不安全**：`_run` 原先用单个 `self._worker`，而 `do_assemble`
   的完成回调里会再调一次 `_run`（继续生成预览），**在回调中直接覆盖了最后一个引用**，
   QThread 可能在仍运行时被析构 → `QThread: Destroyed while thread is still running`
   → 进程 abort（正是"无 Python 回溯的闪退"）。→ 改为列表持有强引用，只回收
   `isFinished()` 的线程；退出前 `wait()` 收尾。回归测试退出码 **0**。
3. **槽函数异常会直接 abort 进程**：PyQt6 里槽函数抛未捕获异常会走 `qFatal()`。
   → 新增 `_guard_slot` 统一兜底（记日志 + 弹窗，程序继续运行），并给
   `remove_row / move_row / add_files / do_assemble / do_preview / show_preview /
   _fmt_reset_default` 等槽加装。
4. **文件对话框改走 Qt 自带实现**（`DontUseNativeDialog`），绕开 GTK3 /
   xdg-desktop-portal 平台主题插件与输入法框架同进程叠加的风险；对话框前后各加一条
   面包屑日志。

### 新增：崩溃取证（下次崩溃可直接定位）

`app/core/logger.py` 启用 `faulthandler`（写入同一个 `logs/assembler.log`）与
`threading.excepthook`。已实测生效：

```
Fatal Python error: Segmentation fault

Current thread 0x00007fb8973010 (most recent call first):
  File ".../xxx.py", line 39 in crash
```

### 若仍闪退，请这样取证

1. 复现一次（会丢失界面上的内容，属预期）；
2. 把 `汇报汇编程序/logs/assembler.log` 发我 —— 崩溃点会有 `Fatal Python error:` +
   调用栈，据此可定位到具体调用。
