# 跨平台打包与一键运行说明

目标：在 **Windows / 麒麟(x86_64·aarch64) / 统信(x86_64·aarch64)** 上一键运行，
带交互界面与预览界面。

## 关键约束：CPU 架构

麒麟/统信同时运行在 x86_64（海光/兆芯）与 aarch64（飞腾/鲲鹏）上。
LibreOffice 便携版与 Python 二进制均**按架构不同**，因此 Linux 侧需分别出包。

## 一、Windows

1. 在已装好依赖的 venv 中：
   ```
   app\.venv\Scripts\python.exe -m pip install pyinstaller
   app\.venv\Scripts\pyinstaller --noconfirm --windowed --name 文档汇编 ^
     --add-data "app\fonts_bundled;app/fonts_bundled" ^
     --add-data "字体包;字体包" ^
     app\main.py
   ```
2. 将 LibreOffice 便携版（Windows 版）解压到 `dist\文档汇编\libreoffice\`。
3. 产出 `dist\文档汇编\文档汇编.exe`，双击即运行；`run.bat` 亦可直接用 venv 启动。

## 二、麒麟 / 统信（分架构出绿色包）

对 **x86_64** 与 **aarch64** 各做一份：

1. 在对应架构的 Linux 机器（或容器）上建 venv 并装依赖：
   ```
   python3 -m venv app/.venv
   app/.venv/bin/python -m pip install -r requirements.txt
   ```
2. 放入对应架构的 LibreOffice 便携版到 `app/libreoffice/`
   （目录结构须为 `app/libreoffice/opt/libreoffice<版本>/{program,share}`；
   确保 `opt/libreoffice*/program/soffice` 存在且可执行）。

   > ⚠️ **不要按 CPU 架构套用同一个 LibreOffice 版本 —— 这是本项目出过事故的地方。**
   > 同一版本号的两个架构，构建所用的 glibc 基线**可能完全不同**：
   > TDF 官方 **25.8.7** 的 x86_64 构建最高只要求 `GLIBC_2.17`，但**其 aarch64 构建要求 `GLIBC_2.34`**
   > （实测 196 个 ELF 中 102 个 > 2.31）。银河麒麟 V10 SP1 只有 glibc 2.31
   > → 便携 `soffice` 起不来 → **预览恒为空，且 `.doc`/`.wps` 也无法转换**（只有 `.docx` 汇编照常），
   > 界面却只显示"无预览"，极难定位。
   >
   > 判定某构建是否可用，**必须逐个 ELF 读真实运行依赖**，且绝不能用 `grep GLIBC_`：
   > 那会命中 ELF 的 `VERDEF`（**导出**符号），把最高支持版本误当成最低要求版本，得出完全相反的结论。
   >
   > ```bash
   > readelf -V <elf> | sed -n '/Version needs/,$p' | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -3
   > ```

   **aarch64 的正确来源（免 root，已验证）**：麒麟官方源 `archive.kylinos.cn/kylin/KYLIN-ALL`
   提供的 **LibreOffice `1:6.4.2-0kylin3`**（`libc6 (>= 2.29)`，含 `libreoffice-core-nogui` 无头版）。
   用随仓库工具重建便携树：

   ```bash
   # 1) 拉取「种子包 + Depends 闭包」的 deb（仅下载，不动系统）
   python tools/fetch_kylin_libreoffice.py --out build/lo_kylin64 \
       --extra libboost-filesystem1.71.0,libboost-iostreams1.71.0,libboost-thread1.71.0,libraptor2-0,librasqal3
   # 2) 组装自包含便携树（ldd 迭代补库 + 改写 fundamentalrc + 生成 LD_LIBRARY_PATH 包装脚本）
   python tools/make_portable_lo_kylin.py --stage build/lo_kylin64 --out app/libreoffice
   # 3) 验收：必须真的能跑起来并转出文件，不能只看文件存在
   app/libreoffice/opt/libreoffice*/program/soffice --version
   ```

   重建时的几个硬约束（漏掉任一条都会"看起来装好了但起不来"）：
   - ldd 补库探测时 `LD_LIBRARY_PATH` **只能放 `program/`**，放进 stage 目录会导致"补 0 个库"；
   - `program/fundamentalrc` 的 `BRAND_BASE_DIR` 必须由绝对路径改为 `${ORIGIN}/..`，
     否则启动只抛**无文本**的 `DeploymentException`；
   - 二进制的 `RUNPATH=$ORIGIN` **对间接依赖不生效**，故 `soffice` 被替换为设置
     `LD_LIBRARY_PATH` 的包装脚本，原脚本改名 `soffice.real`；`python` 侧调用时也应注入该变量；
   - `program/` 下 **`oosplash` 也必须可执行**（真正 exec 的是它，最容易被漏掉）。

   x86_64 侧仍可使用 TDF 官方构建（其 glibc 基线更低，实测最高 2.28，兼容性更好）。
3. 用 PyInstaller 打包（或保留 venv + `run.sh` 直接启动）：
   ```
   app/.venv/bin/python -m pip install pyinstaller
   app/.venv/bin/python -m pyinstaller --noconfirm --windowed --name 文档汇编 \
     --add-data "app/fonts_bundled:app/fonts_bundled" app/main.py
   ```
4. 目录结构（绿色包）：
   ```
   文档汇编_麒麟_x86_64/
     ├─ run.sh            # 一键启动（nohup 后台亦可）
     ├─ 文档汇编.desktop   # 桌面快捷方式（可选）
     ├─ app/
     │   ├─ .venv/        # Python + 依赖
     │   ├─ main.py
     │   ├─ fonts_bundled/
     │   └─ libreoffice/  # 对应架构便携版
     └─ 字体包/
   ```
5. 双击 `run.sh`（或 .desktop）即运行，**无需 root**。

## 三、run.sh 示例

```bash
#!/bin/bash
cd "$(dirname "$0")"
export PYTHONPATH="$PWD/app:$PYTHONPATH"
app/.venv/bin/python app/main.py
```

## 四、字体随附

`app/fonts_bundled/` 已含 方正小标宋简体 / 仿宋_GB2312 / 楷体_GB2312 / 黑体 四款。
程序仅在系统缺失时提示用户安装；成品文档始终按规范写入字体名。
西文「宋体(SimSun)」通常系统自带，若缺失请另行安装。

## 四、实际出包命令与回归测试

本仓库已用 `tools/build_linux_package.py` 取代上面第 3 步的手工 PyInstaller 流程：

```bash
# 输出 汇报汇编程序_国产系统专用_<arch>.zip
python tools/build_linux_package.py --arch aarch64          # 或 --arch x86_64
python tools/build_linux_package.py --arch x86_64 --libreoffice-dir build/libreoffice_x86_64/lo
```

> 打包脚本里的 `os.remove(旧包)` 在受限沙箱中可能被 safe-delete 拦截；
> 遇到时先把旧包 `mv` 走再执行。
> 打包前**务必确认 `app/` 下没有改名保留的废弃引擎目录**——排除规则只精确匹配目录名 `libreoffice`，
> `libreoffice_broken_*` 之类会被原样打进包。

### 两个架构的引擎来源不同（易错，已有前置守卫）

| 包 | 引擎来源 | 版本 / 架构 |
| --- | --- | --- |
| aarch64 | 默认 `app/libreoffice` | 麒麟源免 root 重建的 `libreoffice6.4`，aarch64 |
| x86_64 | 必须传 `--libreoffice-dir build/libreoffice_x86_64/lo` | TDF `libreoffice25.8`，x86-64 |

漏传 `--libreoffice-dir` 时，x86_64 包会打进 `app/libreoffice` 里的 **aarch64** 引擎，
包名与内容不符，装机后表现为「无法预览、无法转换」。脚本现已加**前置引擎架构预检**：
读 `soffice.bin` 的 ELF `e_machine`（183=aarch64 / 62=x86_64）与 `--arch` 比对，
不符则**直接拒绝打包并给出正确命令**，不会产出废包。

### 随包资源目录 `assets/` 与 `ime/`

除代码外，包内还带两个**必需**资源目录（缺了会分别导致「任务栏显示 Python 图标」与
「界面无法输入中文」）：

- `assets/icons/`：16/24/32/48/64/128/256 共 7 张程序图标
  （Qt6 在 xcb 下要求 QIcon **至少 2 张、单张 ≤512px**，否则不写 `_NET_WM_ICON`）；
- `ime/<arch>/`：适配国产系统 Qt6 的 fcitx 输入法插件，**按 CPU 架构分目录**
  （`aarch64/`、`x86_64/` 各含 `libfcitx-qt6-kylin.so` 适配版与 `.orig` 原始版）。
  分架构的原因：插件是二进制，装错架构不但加载不了，还会把本来可用的系统插件挤掉。
  同一份包同时携带两种架构，装机时按 `uname -m` 取用。

打包脚本会打印 `随包输入法插件架构：aarch64, x86_64` 并逐个检查文件是否齐全。

出包后至少核验：

- `启动汇编程序.sh`、`tools/转docx.sh` 的 zip 权限位为 **0755**、`CR=0`、UTF-8 **无 BOM**；
- `app/libreoffice/opt/libreoffice*/program/` 下 `soffice`、`soffice.real`、`soffice.bin`、**`oosplash`**
  均为 0755（`oosplash` 才是实际 exec 入口，最易漏设）；
- 包内无 `__pycache__` / `.pyc` / `usr/` 软链 / 旧引擎残留；
- 包内 `app/core/*.py` 与工作区一致（可直接比 MD5）；
- 包内 `ime/<arch>/*.so` 的 `e_machine` 与目录名一致（183 / 62），`assets/icons/` 为 7 张。

### 回归测试

```bash
python tests/test_opc_package_integrity.py
```

纯离线（不需要 LibreOffice / WPS），构造一份含 VML 图片与 OLE 嵌入对象的源 docx，汇编后校验产出包的
**关系命名空间、悬空 `r:id`、部件存在性、Content_Types 覆盖、同内容去重**，并额外跑一次
**敏感性自检**（临时把 `PKG_R_NS` 指回 `R_NS` 复现历史缺陷，断言校验确实能抓到）。

它守住的是一类**不会报错、只会静默产出"打不开的文件"**的缺陷：
`word/_rels/document.xml.rels` 的子元素若落在 `officeDocument/2006/relationships`
（那是 `r:id` 与关系 `Type` 的前缀命名空间）而不是 `package/2006/relationships`，
解析器会**直接忽略**这些条目，于是 `document.xml` 的引用悬空。
**LibreOffice 严格（直接拒绝加载），WPS 宽容（照常打开）**——所以这类缺陷只在国产系统侧暴露。

> 排查同类问题的要点：看 `.rels` 的**原始文本**。若出现 `<ns0:Relationship xmlns:ns0=...>`，
> 即中招；并且在校验悬空引用时，**只能把命名空间正确的条目计入"已有关系"**，
> 否则会像当初人工排查那样误判为"引用有解"。

### 修复历史产物：`tools/fix_docx_rels_namespace.py`

命名空间缺陷有一个直接后果：**用旧版本产出的汇编成品本身是坏的**。
实测 `测试2/汇编结果（测试2）.docx`（旧版本产出）在 LibreOffice 下直接报
`Error: source file could not be loaded`；经本工具修复后，同一文件可正常转出 86 页 PDF，
图片实际绘制在第 54/76/80 页。也就是说：**用户此前分发出去的含图片/嵌入对象的成品，
在 Microsoft Word / LibreOffice 下可能丢失图片甚至被判损坏**（WPS 宽容，所以未必被察觉）。

```bash
# 默认非破坏式：输出 <原名>_修复.docx，原文件不动
python tools/fix_docx_rels_namespace.py 某成品.docx 某目录/

# 覆盖原文件（先自动备份为 <原名>.bak.docx）
python tools/fix_docx_rels_namespace.py --in-place 某成品.docx
```

它只把 `*.rels` 里误落命名空间的 `<Relationship>` 原地改回 OPC 包命名空间，
其余部件**逐字节保持不动**，并做一次命名空间 / 悬空引用 / 部件存在性复核。

> **更稳妥的做法是重新汇编一遍**：本工具只治"关系命名空间"这一种缺陷，
> 若文档还有其它问题（缺部件、Content_Types 不全等），重新汇编才能一次性对齐。

> 复核相对路径时的坑：关系 `Target` 是相对 `.rels` 所在目录的**上一级**（`word/`）解析的，
> 且**必须按 posix 规则归一化**，不能简单丢弃 `..` 段——
> `../customXml/item1.xml` 指向 `customXml/item1.xml`，
> 而 `word/customXml/item1.xml` 是另一个（不存在的）位置，会把正常文件误报为"缺失部件"。
